# Оновлення десктопного застосунку (Windows)

Десктопний застосунок Elyra для Windows може перевіряти, верифікувати,
завантажувати та встановлювати власні оновлення. Механізм оновлення навмисно
консервативний: він довіряє лише артефактам, підписаним ключем оновлень Elyra
Ed25519, ніколи не встановлює неперевірений інсталятор, а у разі невдалого
оновлення залишає поточну встановлену версію без змін.

## Що доступно зараз

- Підтримувана цільова платформа оновлень: **Windows x64**.
- Кінцева адреса перевірки:
  `https://github.com/imtiredwhenitalk/Elyra/releases/latest/download/latest.json`
- Прийняті ключі інсталяторів у `latest.json`: `windows-x86_64-msi`,
  `windows-x86_64-nsis` та загальний резервний `windows-x86_64`.
- Конфігурація десктопу оголошує `msi` і `nsis` як цільові формати пакетів для
  Windows; робочий процес випуску для Linux явно збирає `appimage` і `deb` за
  допомогою `--bundles appimage deb`. Пакети Linux не використовуються
  механізмом оновлення Windows.

Версія застосунку, показана в **Налаштування → Оновлення**, береться з
`apps/desktop/src-tauri/tauri.conf.json`.

## Керування для користувача

Відкрийте **Налаштування → Оновлення**, щоб:

- бачити встановлену та найновішу анонсовану версії, дату випуску та примітки
  до нього;
- запускати перевірку на вимогу за допомогою **Перевірити зараз**;
- вибирати, чи перевіряє Elyra підписаний канал під час запуску;
- вибирати, чи показує Elyra сповіщення, коли автоматична перевірка знаходить
  оновлення;
- спостерігати за ходом завантаження та перевірки;
- встановлювати підписане оновлення за допомогою **Встановити оновлення**.

Обидва параметри зберігаються в локальній таблиці SQLite `settings` під ключами
`updates_auto_check` і `updates_notify_available`. За замовчуванням вони
увімкнені. Вимкнення автоматичних перевірок не вимикає ручні.

У Windows Tauri завершує роботу Elyra, коли запускається підписаний інсталятор.
Інсталятор типово використовує пасивний інтерфейс, а конфігурація за
замовчуванням встановлює NSIS у контексті поточного користувача.

## Модель довіри

Публічний ключ механізму оновлень — це константа Rust на етапі компіляції у
файлі `apps/desktop/src-tauri/src/updates.rs`, зареєстрована за допомогою
`tauri_plugin_updater::Builder::new().pubkey(UPDATE_PUBLIC_KEY)`. Конфігурація
плагіна в `tauri.conf.json` містить порожнє значення-заповнювач `pubkey`,
оскільки схема конфігурації плагінів Tauri вимагає це поле; під час виконання
його завжди підміняє значення з Rust.

Публічний ключ (можна вільно поширювати):

```text
dW50cnVzdGVkIGNvbW1lbnQ6IG1pbmlzaWduIHB1YmxpYyBrZXk6IDQyREE1QzczREYzNDdCQkEKUldTNmV6VGZjMXphUXV3aEJQcU9IQVArb1NZTEdaQ0FVOUYrQ056LzJVODYydHh0aVdZR0ZudEEK
```

Відповідний приватний ключ **ніколи** не можна додавати до репозиторію. Будь-хто,
хто має цей ключ, може публікувати оновлення, яким довірятимуть наявні
встановлення.

Потік артефактів:

1. Робочий процес випуску підписує скопійовані інсталятори MSI та NSIS
   приватним ключем із `--app-version <version>`.
2. Кожен файл `.sig` містить вихідний текст підпису у форматі base64, а не URL
   чи шлях.
3. `latest.json` містить ці рядки підписів та абсолютні HTTPS-адреси файлів
   випуску.
4. Під час завантаження Tauri перевіряє байти інсталятора за вбудованим
   публічним ключем. Увімкнено `requireSignedVersion`, тому підписана версія має
   збігатися з версією, анонсованою в `latest.json`.
   `download_and_install_update` також викликає `install`, який повторно
   перевіряє байти перед запуском інсталятора платформи.
5. Якщо перевірка маніфесту, підпису, завантаження або верифікації не вдалася,
   Elyra повідомляє про помилку й не замінює жодних файлів застосунку.

Механізм оновлень Tauri не можна налаштувати так, щоб пропускати перевірку
підпису. Не додавайте `dangerousInsecureTransportProtocol`,
`dangerousAcceptInvalidCerts` або `dangerousAcceptInvalidHostnames` до
конфігурації оновлювача.

## Публікація підписаного випуску

1. Одного разу згенеруйте пару ключів (пропустіть, якщо в репозиторії вона вже
   є):

   ```powershell
   npm.cmd run tauri -- signer generate -- -w .tauri/elyra.key
   ```

   Тримайте отриманий файл `.pub` під рукою, а приватний ключ зберігайте поза
   репозиторієм.

2. У репозиторії GitHub створіть такі секрети Actions:

   - `TAURI_SIGNING_PRIVATE_KEY` — **повний вміст** файлу приватного ключа,
     включно з рядком `untrusted comment:`. Робочий процес приймає та
     нормалізує буквальні послідовності `\n`.
   - `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` — лише якщо приватний ключ було
     створено з паролем.

   Ці секрети потрібні для автоматичних оновлень. Робочий процес ніколи не
   записує їх на диск.

3. Одночасно оновіть версію застосунку в `apps/desktop/src-tauri/tauri.conf.json`
   і десктопному `package.json`, а потім надішліть тег `v*` або вручну запустіть
   робочий процес **Release Windows**.

4. Робочий процес **Release Windows** збирає інсталятори, підписує їх, записує
   контрольні суми SHA-256, генерує `latest.json` і публікує всі файли
   `dist/Elyra-*` у випуску GitHub.

5. Переконайтеся, що випуск містить `Elyra-latest-x64.msi`,
   `Elyra-latest-x64-setup.exe`, обидва файли `.sig`, відповідні файли `.sha256`
   і `latest.json`. Потім відкрийте **Налаштування → Оновлення** у встановленій
   збірці та виберіть **Перевірити зараз**.

Якщо `TAURI_SIGNING_PRIVATE_KEY` відсутній, робочий процес усе одно збирає й
публікує звичайні інсталятори, але виводить попередження та пропускає
підписування й створення `latest.json`. Такий випуск безпечно поширювати, проте
наявні встановлення й надалі повідомлятимуть про останню підписану версію, доки
не буде опубліковано підписаний випуск.

## Ротація ключів

Ставтеся до приватного ключа як до постійної інфраструктури. Його заміна
означає, що всі вже встановлені копії Elyra й надалі довірятимуть старому
публічному ключу, тому перед ротацією заплануйте перехідний випуск. Якщо
приватний ключ втрачено або є підозра на його компрометацію, замініть його,
опублікуйте новий підписаний випуск і зобов’яжіть користувачів вручну встановити
цей перехідний випуск.

## Усунення несправностей

- **«Не вдалося перевірити наявність оновлень»** — переконайтеся, що GitHub
  Releases доступний, що `latest.json` є в останньому випуску і що його JSON
  коректний.
- **«Не вдалося завантажити оновлення або перевірити підпис»** — перевірте, що
  вміст `.sig` у `latest.json` відповідає точній URL-адресі інсталятора, що
  версію підписано з `--app-version` і що публічний ключ у `updates.rs`
  відповідає приватному ключу, який використовується в CI.
- **Оновлення не пропонується** — анонсована версія має бути новішою за
  поточну, а маніфест має містити повний запис для поточної цільової платформи
  Windows.
- **Попередній перегляд у браузері** — вебпопередній перегляд не може
  завантажувати інсталятори. Він імітує результат «все актуально» і зберігає
  параметри оновлень у `localStorage`, щоб інтерфейс налаштувань можна було
  перевірити.
