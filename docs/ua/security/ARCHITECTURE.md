# Архітектура безпеки Elyra

## Базовий рівень безпеки

Десктопний клієнт застосовує ешелонований захист навколо межі довіри, де основні дані зберігаються локально:

- Rust/Tauri є привілейованою межею. JavaScript браузера може запитувати команди зі списку дозволених, але не отримує доступу до файлової системи.
- У Windows SQLite створюється за шляхом `%LOCALAPPDATA%\com.elyra.desktop\elyra.sqlite3`; для кожного з'єднання увімкнено зовнішні ключі, журналювання WAL і `secure_delete`.
- Чутливі криптографічні операції виконуються в Rust із використанням AES-256-GCM, системного генератора випадкових чисел, нових nonce, суворих вимог до розміру ключів і перевірки тегу автентифікації.
- Перевірки стану безпеки доступні через `get_security_status`; Security Lab відображає результат «пройдено/не пройдено» і не підміняє його сприятливим, коли серверна частина недоступна.
- Записи аудиту зберігаються локально у `audit_events`, містять лише тип події, результат і деталі, а також обмежені 500 записами. Ключі, токени, тіла повідомлень і паролі ніколи не мають потрапляти до журналу аудиту.

### Зберігання секретів

Сесії хмари та паролі IMAP/SMTP зберігаються у сховищі ключів ОС через
`keyring-rs` (Windows Credential Manager у Windows). Сервіс сховища ключів —
`com.elyra.desktop`; сесії хмари використовують запис `cloud_session`, кожен
поштовий акаунт — `imap-account-<id>`, а токени провайдерів OAuth —
`oauth-account-<id>`. SQLite містить лише застарілий рядок
`settings.cloud_session`, який при першому читанні переноситься до сховища
ключів і потім видаляється. Секрети ніколи не записуються у webview, журнали
або журнал аудиту.

### Межа довіри сервера

Сервер Elyra зберігає лише метадані акаунтів, курсори синхронізації,
сповіщення та необов'язкову конфігурацію SMTP-релею. Він ніколи не отримує
ключів шифрування десктопного застосунку чи паролів IMAP. Коли користувач, що
увійшов у систему, не має локального SMTP-акаунта, вихідні листи надсилаються
через серверний релей і, отже, проходять через SMTP-провайдера сервера; тіло
повідомлення не зберігається сервером Elyra. Користувачі, які не бажають такого
шляху, можуть налаштувати власний акаунт IMAP/SMTP або продовжити роботу лише
локально. Релей вимкнено, доки адміністратор не встановить `ELYRA_SMTP_HOST`.

## Модель загроз

Захищено від:

- Випадкового розкриття відкритого тексту через криптографічну межу та
  некоректного шифротексту.
- Зберігання облікових даних у відкритому вигляді: хмарні токени та паролі
  поштових скриньок зберігаються у сховищі облікових даних ОС, а не в SQLite.
- Пошкоджень, спричинених некоректними зв'язками SQLite або небезпечними
  налаштуваннями локальної бази даних.
- Необмеженого зростання локального журналу аудиту.
- Заяв про безпеку лише на рівні UI, коли команда Rust недоступна.

Ще не захищено від:

- Скомпрометованого користувача ОС або шкідливого ПЗ з доступом до каталогу
  даних застосунку чи розблокованого сховища облікових даних.
- Захоплення акаунта, крадіжки OAuth-токена або зловживання віддаленою
  поштовою скринькою. OAuth провайдера використовує Authorization Code + PKCE
  і зберігає токени в ключниці ОС. IMAP підтримує паролі застосунку та
  `AUTHENTICATE XOAUTH2` через TLS/STARTTLS; SMTP XOAUTH2 поки що не
  реалізовано.
- Повного захисту від фальсифікації даних у форензичному контексті. Локальні
  записи аудиту в SQLite є матеріалом для діагностики, а не довіреним
  віддаленим журналом безпеки.

## Обов'язкові заходи перед продакшном

1. Зберігати токени оновлення акаунта та ключі шифрування у сховищі облікових
   даних платформи (Windows Credential Manager, macOS Keychain, Linux Secret
   Service), ніколи — у SQLite, localStorage, URL-адресах або журналах. Сесії
   хмари, паролі IMAP і набори токенів OAuth провайдерів уже зберігаються у
   сховищі ключів.
2. Додати SMTP XOAUTH2 з оновленням токенів і областями доступів з найменшими
   привілеями. Потік OAuth для IMAP уже використовує PKCE, перевірку `state`,
   перевірку TLS-сертифікатів і оновлення токенів; IMAP/SMTP вже вимагають TLS
   або STARTTLS із перевіркою сертифіката.
3. Додати автентифіковане експортування/резервне копіювання бази даних, UX
   безпечного видалення, блокування при простої та процедуру відновлення.
4. Перед відкриттям сервісу для загалу додати обмеження частоти запитів і
   захист від зловживань для реєстрації та серверного поштового релею.
5. Додати тести структурованого приховування даних і негативні тести для
   кожної межі команд Tauri.
6. Впроваджувати пересилання аудиту на віддалений сервер у режимі лише
   додавання (append-only) лише за згодою користувача та з мінімізацією
   персональних даних (PII).

## Експлуатаційні перевірки

Security Lab виконує локальну перевірку стану SQLite і відображає обмежений
журнал аудиту. Результат `protected` означає, що налаштовані локальні засоби
контролю пройшли перевірку; це не означає, що пристрій або зовнішній поштовий
провайдер є безпечними. Перевірка випуску має включати `cargo test`,
`cargo check`, перевірку синтаксису JavaScript, аудит залежностей і ручний
огляд можливостей Tauri/CSP.
