# Безпека та конфіденційність

Elyra розроблена навколо межі довіри з пріоритетом локальної роботи: пошта залишається на пристрої
користувача, привілейовані операції виконуються в Rust, а додаткова хмарна служба зберігає лише
метадані облікових записів, курсори синхронізації, сповіщення та конфігурацію ретрансляції.

Ця сторінка описує модель безпеки, реалізовану у 0.5.0, зокрема те, що ще **не**
захищено. Це технічний документ, а не сертифікація.

## Цілі безпеки

1. Зберігати вміст поштової скриньки та паролі IMAP/SMTP на пристрої користувача.
2. Не допускати секретів до SQLite, `localStorage`, URL-адрес, журналів і вебперегляду.
3. Вимагати автентифікованого шифрування для локальних криптографічних операцій.
4. Вимагати TLS або STARTTLS для поштових протоколів.
5. Зберігати набір даних сервера мінімальним і обмеженим для кожного користувача.
6. Чесно повідомляти про стан безпеки замість показу хибного сигналу успішної перевірки.
7. У разі некоректної конфігурації блокувати дію (fail closed).

## Межі довіри

### Webview ↔ Rust

Вебперегляд (webview) розглядається як джерело недовірених даних. Він може викликати лише команди,
зареєстровані в `apps/desktop/src-tauri/src/lib.rs`. Він не може відкривати SQLite, читати файли,
звертатися до сховища ключів або виконувати сирові мережеві запити. Rust перевіряє аргументи й
повертає помилки.

`tauri.conf.json` наразі встановлює `csp: null` і `withGlobalTauri: true`. Це навмисний компроміс
0.5.0 заради статичного фронтенду та доступу до Tauri API. Перед тим як вважати вебперегляд
зміцненою межею, рекомендується запровадити сувору політику безпеки вмісту (Content Security Policy)
і зменшити глобальну поверхню.

### Робочий стіл ↔ сховище ключів ОС

Секрети зберігаються за допомогою `keyring` 3 з бекендом `windows-native`, що відповідає
Windows Credential Manager.

- Служба: `com.elyra.desktop`
- Запис сеансу хмари: `cloud_session`
- Запис поштового облікового запису: `imap-account-<id>`
- Запис токенів OAuth провайдера: `oauth-account-<id>`
- Запис ключа API інтеграції: `integration-<provider>` (`virustotal`,
  `google_safe_browsing`)
- Запис приватного ключа ідентичності: `crypto-key-<id>`

Сховище ключів захищене контекстом користувача операційної системи. Elyra не додає другий шар
шифрування на рівні застосунку до значень сховища ключів.

### Робочий стіл ↔ поштовий провайдер

- IMAP: `imap` 2.4 через `native-tls`, лише TLS або STARTTLS.
- SMTP: `lettre` з rustls, лише TLS або STARTTLS.
- Нешифровані поштові протоколи не підтримуються.
- Для IMAP підтримуються паролі застосунків та OAuth 2.0 Authorization Code +
  PKCE. OAuth використовує тимчасове loopback-перенаправлення, перевіряє `state`
  і не передає токени у webview; див. [OAuth провайдерів](oauth.md).
- SMTP XOAUTH2 не реалізовано: для надсилання облікові записи OAuth усе одно
  потребують пароля застосунку або релею Elyra.

### Робочий стіл ↔ сервер Elyra

- HTTPS у виробничому середовищі.
- Токени доступу JWT (Bearer).
- Сервер ніколи не отримує паролів IMAP, ключів шифрування або вмісту поштової
  скриньки.
- Ретрансльовані повідомлення проходять через SMTP-провайдера сервера; сервер Elyra
  не зберігає тіло повідомлення.

### Публічний інтернет ↔ сервер

- Caddy завершує TLS (необов'язковий профіль) і передає запити Nginx.
- Nginx обслуговує статичний сайт і проксує `/api/` до контейнера API.
- PostgreSQL, Redis і API перебувають у приватній мережі Docker.
- За замовчуванням публікується лише порт вебсайту; за TLS — лише 80/443.

## Захист локальних даних

### SQLite

Шлях до бази даних: `%LOCALAPPDATA%\com.elyra.desktop\elyra.sqlite3`.

Кожне з'єднання вмикає:

```sql
PRAGMA foreign_keys = ON;   -- relationship integrity
PRAGMA journal_mode = WAL;  -- crash safety and concurrency
PRAGMA secure_delete = ON;  -- overwrite deleted content
```

`secure_delete` зменшує можливість відновлення видалених рядків, але не є повним
шифруванням диска. Доступ до файлової системи з того самого облікового запису ОС,
резервні копії, знімки тому або інструменти судової експертизи можуть і надалі
розкрити дані.

### Сховище ключів

- Сеанс хмари та паролі пошти зберігаються у сховищі ключів.
- Застарілий рядок `settings.cloud_session` переноситься до сховища ключів під час
  першого читання, а потім видаляється.
- SQLite зберігає метадані облікового запису (хост, порт, ім'я користувача), але не
  паролі.
- Видалення облікового запису видаляє відповідний запис у сховищі ключів.
- Вихід із системи видаляє запис сеансу хмари.

### Журнал аудиту

`audit_events` — локальний журнал для діагностики:

- Записує тип події, результат і подробиці.
- Обмежений 500 записами.
- Ніколи не має містити ключів, токенів, паролів або тіл повідомлень.
- Не є захищеним від підробки чи віддаленим журналом безпеки.

### HTML і відображення вмісту

Читач показує текст повідомлення, а не сирий HTML. Текст екранується перед вставкою
в DOM. Це запобігає виконанню наданого провайдером HTML і сценаріїв у вебперегляді.
Вкладення відображаються як метадані та картки ризику; Elyra не відкриває й не
виконує вкладення у вебперегляді.

## Криптографічні засоби контролю

Межа криптографії робочого столу — `apps/desktop/src-tauri/src/crypto.rs`, побудована
на багаторазовому пакеті `elyra-crypto`.

| Засіб контролю | Реалізація |
| --- | --- |
| Шифр | AES-256-GCM |
| Розмір ключа | 32 байти, згенеровані за допомогою `OsRng` |
| Nonce | 96 біт, новий для кожного шифрування |
| Корисне навантаження | Base64 nonce + ciphertext + authentication tag |
| Цілісність | Тег автентифікації GCM перевіряється під час дешифрування |
| Відбиток | SHA-256, лише для відображення/порівняння |
| Час існування ключа | Знищується (zeroized) при звільненні в `elyra-crypto` |
| Поведінка у разі помилки | Недійсний ключ, пошкоджене корисне навантаження, неправильний ключ або змінений шифротекст повертають помилку |

Security Lab використовує відоме тестове повідомлення й зберігає згенеровані ключі в
пам'яті. Вона демонструє примітив; це не виробнича служба керування ключами.

### Ключі ідентичності (Ed25519)

`apps/desktop/src-tauri/src/keys.rs` керує локальними ключами ідентичності.

- Генерація використовує `ed25519-dalek` із випадковістю ОС.
- 32-байтовий приватний ключ записується лише до сховища ключів ОС як
  `crypto-key-<id>`. SQLite зберігає мітку, публічний ключ, відбиток SHA-256,
  статус і часові мітки.
- Вебперегляд може експортувати лише публічний ключ у броньованому форматі
  (armored) та імпортувати публічні ключі контактів. Жодна команда не повертає
  приватного матеріалу.
- Ротація створює новий активний ключ, позначає попередній як `retired` і видаляє
  попередній запис у сховищі ключів.
- Відкликання позначає ключ як `revoked` і видаляє його запис у сховищі ключів.
  Відкликання виконується локально й не може бути скасоване.
- Публічні ключі контактів зберігаються в SQLite разом із відбитками. Під час
  імпорту перевіряється корисне навантаження base64 і точка Ed25519.
- Ключі ідентичності є основою для підпису та майбутнього наскрізного
  шифрування. Шифрування повідомлень і обмін ключами ще не реалізовані.

### Elyra Shield і розвідування загроз

`apps/desktop/src-tauri/src/shield.rs` виконує локальний аналіз у Rust:

- Перевірка відображуваного імені та адреси відправника на відповідність офіційним
  доменам брендів, включно з нормалізацією punycode і схожими написаннями
  (lookalike).
- Виявлення термінових і загрозливих формулювань, запитів облікових даних або
  оплати, небезпечних розширень вкладень та невідповідності між видимим
  посиланням і цільовою адресою.
- Оцінка від 0 до 100 відповідає станам «Безпечно», «Підозріло» або «Шкідливо» і
  зберігається для кожного повідомлення разом із причинами.
- Локальний аналіз виконується під час імпорту IMAP і під час першого відкриття
  повідомлення.
- Повідомлення про хибні спрацьовування зберігаються локально й відображаються в
  UI.

`apps/desktop/src-tauri/src/threats.rs` виконує додаткові зовнішні перевірки:

- Посилання витягуються з простого тексту та HTML-якорів.
- VirusTotal використовує `GET /api/v3/urls/{base64url}` із `x-apikey` користувача.
- Google Safe Browsing використовує `POST /v4/threatMatches:find?key=...` і
  обробляє URL-адреси пакетами.
- Запити до VirusTotal у безкоштовному тарифі обмежені одним запитом щодо 16
  секунд.
- Вердикти кешуються в SQLite на 24 години, якщо вони відомі, і на 1 годину, якщо
  невідомі.
- Помилки провайдера, обмеження частоти запитів і відсутні ключі повідомляються
  для кожного посилання; вони не блокують відображення повідомлення.
- `settings.external_scanning = "false"` вимикає всі зовнішні виклики. Локальні
  перевірки Shield і надалі виконуються.
- Зовнішні провайдери отримують URL-адреси повідомлення, а не його тіло. Самі
  URL-адреси можуть розкривати конфіденційну інформацію, тому за наявності таких
  побоювань залишайте зовнішнє сканування вимкненим.

`apps/desktop/src-tauri/src/reputation.rs` класифікує домени відправників:

- Результати SPF, DKIM і DMARC аналізуються лише з блоку заголовків повідомлення;
  текст тіла не може їх підмінити.
- Оцінки поєднують правила дозволу й блокування, офіційні домени брендів,
  імітацію та punycode, помилки автентифікації й кешовані вердикти розвідування
  загроз.
- Невідомі домени залишаються нейтральними. Домени зі списку дозволених завжди
  вважаються довіреними, а повідомлення про хибне спрацьовування нейтралізує
  оскаржену оцінку, доки нова розвідувальна інформація не підвищить оцінку.
- Результати кешуються для кожного домену в SQLite і можуть оновлюватися на
  вимогу.

`apps/desktop/src-tauri/src/attachments.rs` аналізує вкладення:

- Визначення типу читає магічні байти й структурні маркери, потім порівнює
  результат із оголошеним MIME-типом і розширенням файлу.
- Локальна оцінка підвищує ризик для виконуваних файлів, сценаріїв, образів
  дисків, файлів Office з макросами, архівів, HTML і SVG, подвійних розширень,
  символів перевизначення напрямку (bidirectional override) в імені та
  невідповідності вмісту й оголошеного типу.
- Локальний аналіз виконується під час імпорту та на вимогу. Він ніколи не
  виконує, не відкриває й не показує попередній перегляд файлу.
- ClamAV — необов'язковий. Якщо його увімкнено, `clamscan` запускається для
  тимчасової копії збереженого вмісту; після цього тимчасовий файл видаляється.
  Відсутність або помилка ClamAV повідомляється як причина й ніколи не блокує
  поштову скриньку.
- Аналіз файлів VirusTotal є необов'язковим і потребує збереженого ключа API та
  явної згоди для кожного файлу. Завантаження мають обмеження розміру й
  підлягають тому ж обмеженню VirusTotal у 16 секунд. Чисті результати
  VirusTotal ніколи не знижують локальне попередження.
- Результати зберігаються для кожного вкладення в SQLite разом із хешем SHA-256,
  виявленим типом, видом, ризиком, оцінкою, причинами, джерелом і часовою
  міткою. Shield повторно використовує збережений ризик під час оцінювання
  повідомлення.

### Що не шифрується

- База даних поштової скриньки SQLite не шифрується Elyra у стані спокою (at
  rest).
- Локальні тіла повідомлень, теми та вкладення зберігаються як дані SQLite.
- Резервні копії й експорт містять відкритий текст повідомлень.
- Дані PostgreSQL на сервері не шифруються застосунком. За потреби
  використовуйте шифрування файлової системи або тому.

Повне шифрування поштової скриньки у стані спокою потребує проєкту керування
ключами й є майбутньою віхою.

## Безпека сервера

### Автентифікація

- Паролі хешуються за допомогою Argon2id і випадкових сіл.
- Токени доступу JWT HS256 підписуються `ELYRA_JWT_SECRET`.
- Секрет має містити щонайменше 32 символи; інакше сервер відмовляється
  запускатися.
- Токени за замовчуванням закінчуються через 24 години.
- Серверні облікові записи досі не мають токенів оновлення, списку відкликання
  або скидання пароля. Сеанси OAuth використовують токени оновлення та відкликання провайдера.

### Авторизація

- Кожен захищений маршрут перевіряє токен Bearer і визначає ідентифікатор
  користувача зі суб'єкта токена.
- Сповіщення обмежені `recipient_id`; позначення сповіщення іншого користувача
  повертає `404`.
- `GET /v1/users/me` повертає лише запис того, хто звертається.
- Курсори синхронізації ключуються за ідентифікатором користувача.

### Валідація вхідних даних

| Вхідні дані | Обмеження |
| --- | --- |
| Електронна пошта | Містить `@`, максимум 320 символів |
| Пароль | Мінімум 12 символів |
| Відображуване ім'я | Не порожнє, максимум 120 символів |
| Заголовок сповіщення | Не порожній, максимум 160 символів |
| Тіло сповіщення | Не порожнє, максимум 4000 символів |
| Тема листа | Не порожня, максимум 200 символів |
| Тіло листа | Не порожнє, максимум 100 000 символів |

Помилки бази даних журналюються на сервері й повертаються як загальна помилка
`internal_error`.

### Ретрансляція

- Увімкнення через `ELYRA_SMTP_HOST`.
- Під час запуску потрібна коректна адреса `ELYRA_SMTP_FROM`.
- Надсилає з адреси ретранслятора, з `Reply-To`, встановленим на
  автентифікованого користувача.
- Не зберігає тіло повідомлення.
- Будь-який зареєстрований користувач може надсилати. Обмежень частоти, квот і
  виявлення зловживань немає.

### Посилення безпеки розгортання

Виробничий стек дотримується таких налаштувань за замовчуванням:

- PostgreSQL і Redis не публікуються.
- API не публікується.
- Вебсайт прив'язується до `127.0.0.1`, якщо увімкнено Caddy.
- Caddy додає HSTS, `X-Content-Type-Options: nosniff`, `Referrer-Policy` і
  видаляє заголовок `Server`.
- Жоден виробничий секрет не має значення за замовчуванням у репозиторії;
  Compose завершується помилкою, якщо обов'язкове значення відсутнє.
- Контейнер API працює з UID/GID `10001`.

## Модель загроз

### Захищено від

| Загроза | Засіб контролю |
| --- | --- |
| Зберігання облікових даних у відкритому вигляді | Сховище ключів для сеансів хмари та паролів пошти |
| Випадкове розкриття токена вебперегляду | У поданні сеансу токен доступу не відображається |
| Пошкоджений або підмінений шифротекст | Перевірка тегу автентифікації AES-GCM |
| Зниження рівня до незашифрованого поштового протоколу | Лише TLS/STARTTLS |
| SQL-ін'єкція в запитах до поштової скриньки | Параметризовані SQL-запити |
| Доступ до сповіщень інших користувачів | Обмеження за отримувачем під час читання й оновлення |
| Витік бази даних паролів | Хеші Argon2id, а не відкритий текст |
| Відсутні секрети сервера | Запуск і Compose завершуються в безпечному режимі (fail closed) |
| Підробка інтерфейсом здорового стану безпеки | Стан безпеки надходить від Rust; помилки відображаються |
| Необмежене зростання локального журналу аудиту | Обмеження у 500 записів |
| Підміна інсталятора під час передавання | Перевірка SHA-256 запускачем (launcher) |

### Не захищено від

| Загроза | Стан |
| --- | --- |
| Скомпрометований користувач ОС або шкідливе ПЗ з доступом до каталогу даних застосунку | Не захищено. Дотримуйтеся гігієни облікового запису ОС, шифрування диска та захисту кінцевих пристроїв |
| Шкідливе ПЗ, здатне читати розблокований Windows Credential Manager | Не захищено Elyra |
| Захоплення облікового запису в поштового провайдера | Залежить від засобів провайдера; використовуйте надійні унікальні паролі застосунків і 2FA |
| Крадіжка токена OAuth | Токени доступу й оновлення зберігаються в ключниці ОС і не потрапляють у webview; шкідливе ПЗ, здатне читати розблоковану ключницю, залишається поза межею захисту |
| Компрометація бази даних сервера | Сервер зберігає метадані й сповіщення; тіла листів не зберігаються, але метадані облікових записів розкриваються |
| Зловживання ретрансляцією | Обмежень частоти та квот ще немає |
| Фішинг або шкідливий вміст повідомлень | Shield додає локальні евристики та необов'язкові перевірки репутації, але жоден фільтр не є досконалим; соціальна інженерія залишається можливою |
| Відмова в обслуговуванні | Обмежень частоти для реєстрації та маршрутів API немає |
| Компрометація ланцюга постачання | Зменшено, але не усунено: робочий `Cargo.lock` актуальний, Rust CI використовує `--locked`, а щотижневі PR Dependabot увімкнено; робочі процеси випуску можуть розв'язувати свіжі версії |
| Повна стійкість до підробки в умовах судової експертизи | Локальний журнал аудиту не виявляє підробку |
| Витік метаданих поштовим провайдерам | IMAP/SMTP неминуче розкривають метадані з'єднання провайдеру |

## Відомі прогалини та подальші кроки

Це задокументовано, щоб адміністратори могли ухвалювати обґрунтовані рішення:

1. **Відкрита реєстрація.** Будь-хто, хто може звернутися до сервера, може створити
   обліковий запис. Додайте код запрошення або схвалення адміністратором перед
   відкриттям для загалу.
2. **Ретрансляція без обмежень частоти.** Додайте обмеження для кожного
   користувача, квоти та моніторинг перед увімкненням ретрансляції для
   недовірених користувачів.
3. **OAuth покриває лише IMAP.** SMTP XOAUTH2 залишається відкритим завданням.
4. **Немає токенів оновлення сервера.** Серверні сеанси закінчуються; сеанси OAuth
   оновлюються в десктопному застосунку.
5. **Немає скидання пароля чи підтвердження електронної пошти.**
6. **Ліберальний CORS.** Обмежте походження (origins), якщо API відкрито
   безпосередньо.
7. **Немає CSP.** `tauri.conf.json` має `csp: null`; посильте захист, перш ніж
   вважати вебперегляд суворою межею.
8. **Немає шифрування поштової скриньки у стані спокою.**
9. **Немає планової синхронізації.** Синхронізацію запускає користувач.
10. **Redis не використовується.** Його розгорнуто для майбутніх сеансів, черг і
    роботи в реальному часі.
11. **Shield — евристичний.** Виявлення не є гарантією. Зовнішні перевірки
    репутації залежать від ключів і квот провайдерів користувача.
12. **Ще немає наскрізного шифрування.** Ключі ідентичності існують, але підпис
    повідомлень, обмін ключами та доставка зашифрованої пошти — майбутня робота.
13. **Зовнішнє сканування розкриває URL-адреси.** VirusTotal і Google Safe
    Browsing отримують посилання, витягнуті з відкритих повідомлень, якщо
    зовнішнє сканування не вимкнено.
14. **Сканування вкладень — евристичне.** Локальна класифікація виявляє відомі
    небезпечні типи, але не є повноцінним антивірусом. ClamAV потрібно встановити
    й увімкнути окремо, а завантаження до VirusTotal розкриває файл третій
    стороні навіть за наявності згоди.

## Контрольний список безпеки для адміністраторів

Перед публічним відкриттям сервера Elyra:

- [ ] Використовуйте HTTPS із дійсним сертифікатом (профіль Caddy або зворотний проксі).
- [ ] Встановіть унікальний `ELYRA_JWT_SECRET` щонайменше з 32 випадкових символів.
- [ ] Встановіть надійні унікальні `POSTGRES_PASSWORD` і `REDIS_PASSWORD`.
- [ ] Тримайте PostgreSQL, Redis і API поза публічною мережею.
- [ ] Обмежте брандмауер SSH, HTTP і HTTPS.
- [ ] Опублікуйте SPF, DKIM і DMARC для домену, з якого надсилає ретранслятор.
- [ ] Використовуйте окрему поштову скриньку ретранслятора або транзакційного провайдера.
- [ ] Додайте обмеження частоти для реєстрації та ретрансляції до відкриття публічної реєстрації.
- [ ] Створюйте резервні копії PostgreSQL і перевіряйте відновлення.
- [ ] Стежте за журналами API та помилками ретрансляції.
- [ ] Вирішіть, чи прийнятна відкрита реєстрація для вашої аудиторії.
- [ ] Повідомте користувачів, що ретрансльовані листи проходять через SMTP-провайдера сервера.

## Контрольний список безпеки для користувачів

- [ ] Завантажуйте лише з офіційної сторінки випусків і перевіряйте контрольну суму.
- [ ] Використовуйте паролі, призначені для застосунків, а не основний пароль провайдера.
- [ ] Увімкніть 2FA в поштового провайдера.
- [ ] Оновлюйте Windows і Elyra.
- [ ] Використовуйте шифрування всього диска, якщо пристрій може бути втрачено.
- [ ] Ставтеся до JSON-експорту та резервних копій бази даних як до конфіденційних даних.
- [ ] Виходьте з Elyra Cloud на спільних пристроях.
- [ ] Видаляйте невикористані поштові облікові записи, щоб їхні записи у сховищі ключів були видалені.

## Реагування на інциденти

Якщо ви підозрюєте компрометацію:

1. **Поштовий обліковий запис:** відкличте пароль застосунку в провайдера,
   видаліть обліковий запис в Elyra та створіть новий пароль застосунку.
2. **Обліковий запис Elyra Cloud:** змініть пароль на сервері, вийдіть з системи
   на всіх пристроях і перегенеруйте `ELYRA_JWT_SECRET`, щоб зробити всі токени
   недійсними.
3. **Сервер:** перегенеруйте `ELYRA_JWT_SECRET`, паролі бази даних і Redis та
   облікові дані SMTP ретранслятора; перегляньте журнали API; відновіться з
   достовірної резервної копії, якщо є сумніви щодо цілісності даних.
4. **Пристрій:** від'єднайте від мережі, запустіть захист кінцевих пристроїв,
   перегенеруйте всі облікові дані, збережені у сховищі ключів, і
   перевстановіть систему, якщо шкідливе ПЗ підтверджено.
5. **Зловживання ретрансляцією:** вимкніть `ELYRA_SMTP_HOST`, перегенеруйте
   облікові дані ретранслятора та перегляньте журнали провайдера.

Оскільки списку відкликання токенів немає, найшвидший спосіб зробити всі сеанси
недійсними — перегенерувати секрет JWT.
